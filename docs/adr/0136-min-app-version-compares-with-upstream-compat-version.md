# 最低应用版本与上游兼容版本比较，应用版本只给自己用

本项目是上游 ArcReel 的 fork，版本号从 `0.1.0` 重新起算。官方模型目录与市场条目里的最低应用版本（`min_app_version`，`docs/adr/0103`）按上游 ArcReel 的版本号标注，例如 `0.35.1`。拿 fork 自己的版本号去比，`0.1.0` 永远低于上游的门槛，目录同步来的模型和市场条目会一直停用。决定分开两个版本：

- **应用版本**：`pyproject.toml` 的版本，由 release-please 维护，用于「关于」页、版本接口、镜像标签与发版，以及检查本仓库有没有新版本。
- **上游兼容版本**：`lib/app_version.py` 的 `UPSTREAM_COMPAT_VERSION`，表示本 fork 已包含到哪一版上游 ArcReel 的内容。目录查询（`lib/catalog/query.py`）、市场条目的门槛与安装检查（`server/routers/market.py`）、自定义端点定义的版本提示（`server/routers/custom_endpoints.py`）都只和它比较。
- 界面上的门槛提示只说需要兼容哪个 ArcReel 版本，例如「需要相容 ArcReel 0.36.1 以上的版本」，不出现 fork 自己的版本号。端点导入提示的「目前」也是上游兼容版本。

## 取值

取值是「已完整包含的上游 main 提交」对应的门槛值：上游 main 在某个提交时 `.release-please-manifest.json` 记录 `X.Y.Z`，此后合入的内容按 0103 的规则标 `X.Y.(Z+1)`。本 fork 的分叉点 `d49709549` 是上游 main 的提交，当时清单记录 `0.35.0`，fork 包含 `v0.35.0` 及其后到分叉点的全部上游提交，所以取 `0.35.1`。上游后来发布的 `v0.36.0` 里有 26 个提交不在 fork 中，所以不取 `0.36.0`。

`0.35.1` 也覆盖了上游在分叉点之后、`v0.36.0` 之前才合入的内容，例如 Grok 配音。这类模型挂的调用端点在 fork 的端点清单里不存在，目录读取时按未知端点处理，不会因为版本门槛放行就变得可以调用。只有挂在已有端点上、又依赖分叉点之后才合入的代码的模型会被误放行，同步上游时要核对。

## 同步上游时

1. 合入上游 main 到某个提交后，看那个提交上的 `.release-please-manifest.json`，记为 `X.Y.Z`。
2. 只有完整合入了到该提交为止的上游 main，才把 `UPSTREAM_COMPAT_VERSION` 改为 `X.Y.(Z+1)`；合入的正好是发版提交 `vX.Y.Z` 时同样取 `X.Y.(Z+1)`。只挑选部分提交移植时不改。
3. 检查上游目录里门槛等于新值的模型，确认它们依赖的代码都已合入。
4. 本 fork 新增的调用端点，起始版本填当时的 `UPSTREAM_COMPAT_VERSION`，测试拦下高于它的值。

## Considered Options

- **fork 版本号接在上游后面（例如 `0.36.x`）**：比较不用改，但 fork 的版本号会和上游的同号版本混淆，也推翻了从 `0.1.0` 起算的决定。
- **取 `0.35.0`**：最保守，但上游在 `v0.35.0` 之后合入、fork 已经包含的 31 个模型会一直停用。

## Consequences

- 修订 `docs/adr/0103`：本仓库里的起始版本改按上游兼容版本填写，见该文的修订说明。
- 「关于」页检查新版本改查本仓库的 GitHub Release，不再拿上游的版本号和 fork 的版本号比较。
- 上游兼容版本落后时，新模型和新条目会停用并显示所需的 ArcReel 版本，这是保守的一侧。
- 市场安装上报给官方服务的 `app_version` 仍是本应用的版本；官方服务默认关闭（`docs/adr/0133`）。
