# 编辑单元经服务端合并的 CRDT 房间多人即时共编

多位成员同时打开同一个项目时，原来的做法是「改完再保存」，再用编辑起点（`base`）拒绝覆盖别人刚改过的字段。这只能防止静默覆盖，做不到像共同编辑文档那样一起打字。决定如下。

**单位是编辑单元**：界面上的一个编辑区（项目概述、创作灵感、一个资产、一个衍生形象、一集自带的原文、剧本里的一格）对应一个房间，键为（项目，种类，单元键）。剧本里一格的单元键是去掉 `scripts/` 前缀的剧本文件名加 `#` 加编号，同一格不会因写法不同被分成两个房间。

**房间内容是存储里的字段**：每种单元在 `server/services/collab/units.py` 登记读写两个函数。读出的是存储里白名单内的字段，写回只交出改过的顶层字段，走与各 REST 接口同一套修改逻辑（项目更新、资产更新、剧本批量编辑的 `update`）。文档结构是：对象为 `Map`，清单为 `Array`，对象上的字符串为 `Text`，清单里的字符串保持原子值（`lib/collab/ydoc_json.py` 与 `frontend/src/collab/ydoc-json.ts` 同一规则）。这样提示词的结构化字段、台词清单里的每一句，都能多人同时改。

**服务端合并并写回**：服务端（pycrdt）持有每个房间的文档，转发 y-protocols 的同步与在线状态消息。文档改动后安静 0.8 秒（最长 3 秒）写回改过的字段，变更来源记为 `collab`、改动者记为最近一位改动的成员。界面对 `collab` 来源只刷新数据，不弹「谁改了」的提示：同一个编辑区里已经看得到对方在打字。写回被拒（内容不合规）时把原因告诉房间里的每个人。写之前核对要写的字段：存储里的值与房间上次见到的不同，说明别处刚改过而中枢还没重读（Agent 的写入事件还没到，或轮询还没轮到），这时不写，先把那次改动按下面的三方合并并进文档、转发给成员，再按合并后的内容重写。连续 3 次都对不上就报写回失败，修改留在文档里，等下一个安静期（0.8 秒）再试；每个安静期最多核对 3 次，别处一直在写也不会空转，房间关闭后不再试。中枢按记录认出自己的写入：每次写回交给单元之前，先记下要写的值与这些值对应的文档状态；写成后清掉。写入报错、结果不明（例如提交之后连线中断）时记录留着，之后核对、重读或轮询在存储里读到记录里的值，就认定那次写入已落地，合并基准前进到记录的文档状态，不当成别处的改动再合并一遍；存储里是别的值时作废记录，按别处的改动照常合并。写成之后读回失败时按写下去的值记下，下次重读再校正。写回一旦开始就做完，不可取消，避免文件已写而房间仍记着旧内容。关停与关闭房间因此会等进行中的写回结束：不属于项目的单元由各自的读写决定要等多久（数据库操作受连接池与驱动的时限约束），项目单元的写入在线程里进行，同样等它写完。中枢不给读写另加时限：放进线程的读写不能中途停下，加了时限只会把已经写成的写入报成失败。最后一人离开后稍等再写回并关闭房间。

**外部改动按三方合并插进文档**：房间记下「文档与存储一致时」的状态。Agent、后台任务或其他接口改了同一个单元时，从那份状态出发套上存储的新内容，得到外部改动的增量，再合并进当前文档。还没写回的输入由 CRDT 与外部改动合并，不会被覆盖。别处删掉了某个字段（剧本里一格的选填字段读出时会省略）：没人改过就从文档里删掉；有人改过、还没写回，就保留这个字段在文档里的整段内容并写回。CRDT 自身的规则是删除胜过对字段内部的修改，照它做会把正在打的字连同字段一起丢掉，所以这里让修改胜过删除。存储里的新值正好等于文档里还没写回的字（别处写入的就是这段字）时不再合并，否则同一段字会出现两次；别的字段也没有没写回的修改时，合并基准前进到当前文档。订阅生效时先重读一次，补上房间打开到订阅生效之间的改动。

**本机修改以界面看到的内容为基准**：输入框的 `onChange` 给出的是整段新文字，基准是上一次渲染的内容。界面看到的就是文档当前内容时直接套差异；远端更新已到、界面还没重绘时，从渲染那一刻的文档状态出发算出本机增量再合并，不会把刚到的远端修改改回去。撤销只撤本机来源的修改。

**连线**：浏览器每个分页一条 WebSocket（`/api/v1/collab`），所有房间共用。浏览器的 WebSocket 不能带请求头，连上后第一条消息送登录令牌；只接受网页登录，不接受 API Key 与内嵌 Agent，之后每 60 秒复核账号仍有效。首次连线 5 秒内没就绪、或认证被拒时，编辑区退回「改完再保存」，`useEditUnit` 的行为与以前相同。

**已知的残余风险**：以下情况在审查中用探针复现过，代价与发生概率都低，暂不处理。

- 别处的写入恰好落在中枢写入之后、读回之前，会被当成读回内容吸收，文档里看不到它（主线行为相同）。
- 核对与写入之间仍有空隙：项目单元是同一个线程里先读后写，隔着各单元自己的加锁；不属于项目的单元隔着一整次异步读写来回。别处恰好落在空隙里的写入会被覆盖；要完全排除，需要各单元在自己的锁内核对。
- 成员和别处同时新增存储里原本没有的同一个字段时，只有一方的内容留下。
- 「修改胜过删除」只认在线、还没写回的修改：离线时改了某个字段、期间它被别处删掉，重连后这份离线修改会丢；字段被删后成员把修改改回原样，字段会被写回来。
- 存储会规整写入内容（去掉结尾空白、统一 Unicode 形式、排序清单）时，别处写入的正是还没写回的字的规整形式，判断不出两者相同，会当成别处的改动合并，同一段字可能出现两次。
- 别处写入的正是还没写回的字，而其他字段也有没写回的修改时，合并基准要等随后的写回才前进；这之间别处再改同一个字段，同一段字可能出现两次。

**在线状态**：光标与选区以 Yjs 相对位置广播，远端改动后按相对位置把本机光标放回原处；其他人的光标画在输入框上并带名字。每个页面另有一个不承载内容的房间（种类 `page`）只转发鼠标指针，位置按「锚点元素 + 在它内容区里的比例」表示，不同窗口大小与卷动位置都对得上。

**单进程**：房间与在线名单只在服务进程的内存里，部署只能运行一个服务进程；关停前写回所有未写回的内容。

**不属于项目的单元**：全局资产库条目、工作区记忆文件这类单元不属于任何项目，房间的 `project` 为空串，读写是协程。它们没有项目事件流可订阅，中枢在房间打开期间每 3 秒重读一次，别处（接口、Agent）的改动照样三方合并进文档。项目设置也是一个房间，内容是项目文件里的设置字段，写回与项目 PATCH 共用 `server/services/project/project_settings_patch.py`；写回被拒时把与接口相同的错误文案告诉房间里的每个人，修改留在文档里，补齐后再写回。参考图只能上传换掉。

**不在范围内**：供应商、凭证、自定义端点与其余全局设置随连线中心重做时再改成即时协作；集原文的类型（小说 / 剧本）改动要确认受影响的集，仍单独提交。
